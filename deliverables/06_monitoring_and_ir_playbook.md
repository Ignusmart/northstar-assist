### Logs Insights queries (log group `/aws/bedrock/vantage-aria/invocations`)

**Q1: answered without retrieval (S4)**
```
filter operation = "ConverseStream" and identity.arn like /68dqb/
| parse identity.arn "AgentCore-MicroVM-*-DEFAULT" as session
| fields @message like /toolResult/ as hasRetrieval
| stats count(*) as turns, sum(hasRetrieval) as turnsWithRetrievedContext,
        max(input.inputTokenCount) as maxIn, sum(output.outputTokenCount) as outTokens by session
| filter turnsWithRetrievedContext = 0 and maxIn > 0
| sort outTokens desc
```
(`maxIn > 0` excludes requests the guardrail blocked on input, which are logged with 0 tokens.)

**Q2: zero-chunk retrieval (S5)**
```
filter operation = "ConverseStream" and identity.arn like /68dqb/ and @message like /"retrievalResults":\[\]/
| stats count(*) by bin(1h)
```

**Q3: guardrail activity per session, by policy (investigation)**
```
filter operation = "ConverseStream" and identity.arn like /68dqb/ and output.outputBodyJson.stopReason = "guardrail_intervened"
| parse identity.arn "AgentCore-MicroVM-*-DEFAULT" as session
| parse @message /"type": ?"(?<policyType>PROMPT_ATTACK|[A-Z_]+)", ?"confidence"/
| stats count(*) as blocks by session, policyType
| sort blocks desc
```
(Tested: it returned the 6 injection sessions as `PROMPT_ATTACK`. Topic blocks have no `confidence` field, so they show with an empty `policyType`; open those records to see the topic name.)

**Q4: which documents reached the model (investigation)**
```
filter operation = "ConverseStream" and identity.arn like /68dqb/
| parse @message /s3:\/\/northstar-assist-kb-jaqr-101020\/(?<doc>[^"\\]+)/
| filter ispresent(doc)
| stats count(*) as turns by doc
| sort turns desc
```
(Tested: it returned `html/company_policies_handbook.html` (8 turns) and `csv/employee_directory.csv` (2 turns) for the test window.)

# Part 2: Incident response playbook: suspected prompt injection

**Use this playbook when:**
- alarm `NorthstarAssist-GuardrailInterventions` or `NorthstarAssist-PromptAttackBlocks` fires,
- or a user reports that Northstar Assist behaved strangely (ignored its instructions, revealed its system prompt, gave a wrong or odd policy answer, or exposed data),
- or a document in the knowledge base is suspected of containing instructions to the model.

**Severity guide:**
- **SEV-3:** blocked attempts only, nothing got through.
- **SEV-2:** an injected instruction changed an answer, or a document carries an instruction.
- **SEV-1:** confidential data was disclosed, or wrong guidance was acted on.

Set all commands up once:
```bash
export AWS_REGION=us-east-1
LOGS=/aws/bedrock/vantage-aria/invocations
HARNESS=NorthstarAssist-dDBp3qRpDd
ROLE=AmazonBedrockAgentCoreHarnessDefaultServiceRole-68dqb
BUCKET=northstar-assist-kb-jaqr-101020
KB=5CO8QOAYFZ
```

## Step 1: Triage (first 15 minutes)
1. Open the alarm.
   - **Console:** CloudWatch → Alarms → `NorthstarAssist-GuardrailInterventions` → History. Note the time window and the datapoint value.
   - **CLI:**
     ```bash
     aws cloudwatch describe-alarm-history --alarm-name NorthstarAssist-GuardrailInterventions --history-item-type StateUpdate --max-items 5
     ```
2. Find **which sessions** triggered it, and **which policy**.
   - **Console:** CloudWatch → Logs Insights → log group `/aws/bedrock/vantage-aria/invocations` → run **Q3** over the alarm window.
   - Note each `session` (the MicroVM ID) and its `policyType`:
     - `PROMPT_ATTACK` → injection.
     - Topic → scope evasion.
     - `EMAIL`/`PHONE` → harvesting.
3. **Decide whether anything got through.** Look for the same sessions with turns where `stopReason` is `end_turn` (an answer was given), not `guardrail_intervened`:
   ```bash
   aws logs filter-log-events --log-group-name $LOGS \
     --start-time <epoch-ms-start> --end-time <epoch-ms-end> \
     --filter-pattern '"AgentCore-MicroVM-<session-id>"' \
     --query 'events[].message' --output text
   ```
   - **All blocked → SEV-3.** Continue to Step 2, but containment can be light.
   - **Any answer given in an attacking session → SEV-2 or higher.**
4. Run **Q1**. Answers with **no retrieval** in the same window suggest the model was steered away from the knowledge base.

## Step 2: Contain
Pick the actions that match the severity. Each one is reversible.

| Action | When | How |
|---|---|---|
| **Block the user** | The attacker is a known employee account | In the Streamlit app, disable the user (or remove their SSO group) and rotate `APP_PASSWORD`. Look up the user from the **app log** by session time. |
| **Stop all traffic to the agent** (kill switch) | SEV-1/2 while investigating | Remove the app role's `bedrock-agentcore:InvokeHarness` / `InvokeAgentRuntime` permissions, or stop the Streamlit service. Console: IAM → Roles → the app role → remove the policy. |
| **Freeze the knowledge base** | A **document** is suspected (indirect injection) | Don't start any sync. Restrict writes to the bucket: S3 → `northstar-assist-kb-jaqr-101020` → Permissions → Bucket policy → add a Deny on `s3:PutObject`/`s3:DeleteObject` for everyone except the investigators. |
| **Tighten the guardrail** | The attack phrasing got through | Bedrock → Guardrails → `northstar-assist-guardrail` → edit the draft (add a denied topic or word filter) → **Create version** → update the harness `guardrailConfig` to the new version (Agents → NorthstarAssist → Update → Parameters). The IAM Deny accepts any version of this guardrail. |
| Do **not** | — | Don't widen IAM or detach the guardrail to "make it work". Don't delete logs or documents; they're evidence. |

## Step 3: Investigate
1. **Reconstruct the conversation.** For each suspicious session, pull every turn:
   ```bash
   aws logs filter-log-events --log-group-name $LOGS --filter-pattern '"AgentCore-MicroVM-<session-id>"' \
     --query 'events[].message' --output json > session.json
   ```
   - Read `input.inputBodyJson.messages` (what the user sent) and `output.outputBodyJson` (what the model said).
   - Read `trace.guardrail` (what was assessed and blocked).
   - Check whether the **system prompt** or confidential content appears in any output.
2. **Check for indirect injection.** Run **Q4** for the window and list the documents whose chunks reached the model. For each document involved, look for text addressed to the model:
   ```bash
   aws s3 cp s3://$BUCKET/<path/to/doc> - | grep -niE "ignore (all|previous)|system:|you are now|developer mode|override|do not tell"
   ```
3. **Check whether the document changed recently.**
   - **Console:** AgentCore → Knowledge Bases (KB) → `northstar-assist-kb` → `northstar-documents` → **Sync history**. Look at the **modified** count and its time.
   - **CLI:**
     ```bash
     aws bedrock-agent list-ingestion-jobs --knowledge-base-id $KB --data-source-id 0YC45VVULG \
       --sort-by attribute=STARTED_AT,order=DESCENDING --max-results 5
     aws logs filter-log-events --log-group-name /aws/vendedlogs/bedrock/knowledge-base/APPLICATION_LOGS/$KB \
       --filter-pattern '"<document-name>"'
     ```
   - If versioning and access logs are enabled (a pre-launch condition), list versions with `aws s3api list-object-versions --bucket $BUCKET --prefix <key>` and find the uploader in the S3 access log (`REST.PUT.OBJECT` on that key).
4. **Check for bypass attempts.** Look for AccessDenied errors from model overrides, which mean the guardrail-less or unapproved-model path was tried:
   ```bash
   aws logs filter-log-events --log-group-name /aws/bedrock-agentcore/runtimes/harness_NorthstarAssist-2X0VnqAgmt-DEFAULT \
     --filter-pattern '"AccessDenied"'
   ```
5. **Identify the person.**
   - Match the session times to the **app log** (user + `runtimeSessionId`).
   - The invocation log alone can't name the employee. If the app log is missing, record that as a gap in the incident report.
6. **Scope the impact.** Run Q4 and Q1 over the whole period since the first malicious turn (or since the suspicious document's sync), and list every answer that could have been affected.

## Step 4: Eradicate and recover
- **Malicious document:**
  1. Restore the last known-good version with `aws s3api copy-object … ?versionId=<good>`, or delete the file.
  2. **Re-sync the knowledge base:**
     ```bash
     aws bedrock-agent start-ingestion-job --knowledge-base-id $KB --data-source-id 0YC45VVULG
     ```
     Until the re-sync runs, **the index keeps serving the poisoned chunk**.
  3. Re-ask the affected question in a **new** Playground session to confirm the clean answer.
- **Guardrail gap:** keep the new guardrail version, and re-run the edge-case tests from the launch-readiness report.
- **Remove containment in reverse order** once the fix is verified: restore bucket writes, then app access, then the user (if cleared).

## Step 5: Communicate and close
1. **Notify:**
   - SEV-1/2: security lead + system owner within 1 hour.
   - **Data disclosure (PII, customer financials):** privacy/legal, as required.
   - **Wrong guidance acted on:** the affected employees, with a correction.
2. **Record** in the incident ticket: timeline, sessions, prompts, documents, what got through, containment, root cause, and fixes.
3. **Follow up within 5 days:**
   - add the attack phrasing to the edge-case test suite,
   - tune the alarm thresholds,
   - and track the open gaps: app-level user logging, S3 versioning + access logs, data minimization of the knowledge base.
